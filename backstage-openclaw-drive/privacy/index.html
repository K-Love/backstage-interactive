Who operates the app

The OAuth app name is Backstage OpenClaw Drive. I, Kevin Love, operate it as Backstage Interactive. It is a private tool for my own use. It is not a public product on the website.

I am not the operator of OpenClaw in general. OpenClaw is the software this tool runs. This policy is about this app only.

What this policy covers

This policy is about the private Drive tool described on the app page. It does not cover the website contact forms, KeyProse, WildThesis, or a client site.

The website forms and this tool are different. The forms on the studio homepage, Website Fixes, and the Google Business Profile page collect the notes described in the website Privacy Policy. Those forms do not request Google Drive. Sending a form does not authorize this app, and authorizing this app does not send a website form.

Drive access now

A dedicated Google account has authorized Drive for this app. The app is in Testing mode, not a production publishing status. The account address, test users, and credentials are not printed here.

The scope is https://www.googleapis.com/auth/drive. It allows the app to view, create, edit, and delete Drive files that account can access.

The connector is set to a folder named Backstage Work. That restriction is in the connector configuration. It is not a boundary Google enforces on the scope.

What was tested

One test used a 171-byte file. The upload, the download, and a byte-for-byte comparison passed. The file remains in Deliverables and belongs to the dedicated automation account. That is one test. Routine Drive exchange is not enabled, and Chief integration is not enabled.

The 7-day and 30-day rules for transfer and staging copies apply if that exchange is turned on. They are a future requirement, not a workflow running now.

Server and other services

OpenClaw runs on a DigitalOcean server. Daily backups of that server are enabled. I had already confirmed that they were turned on. DigitalOcean’s documents for the daily plan describe a standard seven-day rolling retention. I checked those documents on November 7, 2026: the backups quick start (opens in a new tab) and how backups convert to snapshots (opens in a new tab). Seven days is that documented standard. It is not a fresh audit of this account’s expiry setting. A copy can remain until that restore point actually expires.

A full-server backup image is not edited to delete one file. Daily backups are not routinely converted into snapshots kept without an end date. Restoring a backup has not been tested. Manual snapshots, exported backups, and migration archives are a separate hold. The seven-day daily rule does not cover them.

OpenClaw uses Telegram for conversations with me. The public website is hosted on Netlify and does not store this tool’s Drive files. Routine Drive exchange and Chief integration are not enabled.

How Drive content is used

When OpenClaw’s AI reads a Drive file, it reads the file contents. The relevant content is sent to Abacus.AI for processing only, to carry out the request. OpenClaw does not store that content anywhere other than Google Drive, apart from the copies described in How long material is kept, such as temporary transfer copies.

OpenClaw does not use Google Drive data to train AI models. We use Abacus.AI under terms that do not permit using this data to train models, as stated in Abacus.AI’s privacy policy (opens in a new tab).

Backstage OpenClaw’s use and transfer of information received from Google APIs to any other app will adhere to the Google API Services User Data Policy (opens in a new tab), including the Limited Use requirements.

Drive data is used only to provide and improve user-facing features of OpenClaw for Kevin, never sold, never used for advertising, never used to train generalized AI models, and no human reads it unless the user gives permission, it is needed for security or abuse investigation, to comply with law, or it is aggregated and anonymized for internal operations.

How long material is kept

This is the operating policy I adopted on November 7, 2026. It is the rule I intend to follow. It is not a report that the server already enforces it. No cleanup was run when I adopted it.

Saved work stays until I ask for it to be deleted, or until an expiry I set for that project. Other copies follow the manual targets in the table, including temporary transfer copies. Automatic cleanup is not fully implemented. A deletion request covers controlled live copies first. Backups and outside providers are a separate step. Daily DigitalOcean backups follow that plan’s standard seven-day window. Manual archives do not. Revoking Google access does not delete copies. None of the day counts is a guaranteed deadline or a full automatic purge.

Deleting material

Deletion under this policy is a manual process. The tooling for a complete deletion is not implemented. The steps below are the rule, not a claim that a button already does them.

  • Confirm that the request is mine, and confirm the precise scope.
  • Deleting a Drive original has to be an explicit choice. Deleting a cache or staging copy is not that choice.
  • Pause related transfers, tasks, and any queue that would import the material again.
  • Write the content-free receipt outside the server recovery image.
  • Find the controlled copies, indexes, logs, and backups the scope covers. Remove those. Leave unrelated work in place. Confirm before the live copy is removed.
  • The target for that controlled live deletion is within 7 calendar days after the scope is confirmed. That is a manual target, not a service level.
  • Closing the request is a later step. It waits until backup expiry and provider limits are accounted for. Live deletion and full closure are not the same event.
  • Then check that no live or indexed copy remains, and that nothing is queued to bring the material back.

Removing a file link is not physical sanitization of a disk. A file in Google Drive Trash can still be recovered. It is not permanent erasure. A copy already held by Abacus.AI or Telegram is deleted through that service’s own process. Deleting a copy on this server does not erase it there.

Revoking Google access

Revoking the Google authorization invalidates that authorized access. Copies already downloaded stay where they are. Deleting the active credential file does not remove credentials that remain inside older backups. Tracking when those backups expire, and rotating credentials after a compromise or a restore, are manual steps. Manual archives are separate from the seven-day daily backups.

Restore safeguard, not yet drilled

This is the restore rule. It has not been implemented as a drill, and a restore has not been run successfully under it.

A restore is done in isolation. The gateway, the Telegram sender, transfers, and paid tasks stay off. The deletion ledger outside the server image is consulted. Deletions made after the backup are applied again. Stale credentials and queues are removed. Indexes are rebuilt. The result is checked before the server is put back on the network.
